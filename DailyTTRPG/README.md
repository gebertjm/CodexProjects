# DailyRPG

DailyRPG is a beginner-friendly local starter stack with:

- PostgreSQL in Docker for persistence
- A small Node.js + Express backend
- A plain HTML/CSS/JavaScript frontend
- Docker Compose orchestration and simple helper scripts
- Adminer for local database browsing and SQL queries

## What was created

```text
DailyRPG/
  backend/              Express API + PostgreSQL client
  frontend/             Static site served by nginx
  db/init/              PostgreSQL initialization SQL
  scripts/              PowerShell helpers for setup and verification
  docker-compose.yml    Local stack orchestration
  .env.example          Environment variable template
  .gitignore
  README.md
```

## Why this setup

- `postgres:16-alpine` keeps the database lightweight and common.
- `node:20-alpine` is a stable current LTS-style choice for a simple starter backend.
- `nginx:alpine` serves the frontend and proxies `/api/*` to the backend, which avoids CORS setup for beginners.
- `adminer:4` gives you a simple browser-based SQL UI for local development.
- Docker Compose health checks make startup more reliable.

### Living World State Foundation

Stage 5J.1 formalizes the backend model for async living campaigns. Authored content remains package/file based, while mutable world-instance state, entity/location/scene state, affordance lifecycle, per-character knowledge, and structured world events live in the database. The backend assembles character-limited scene views through `CharacterSceneViewService` and exposes them at `GET /api/play/current-scene` for the future Flutter rich scene UI.

Key rule: content defines what can happen, DB state records what has happened, character knowledge controls what the player can see, and events record meaningful mutations.

### Environment Context And Rich Description Overlays

Stage 5J.2 adds authored environment context to character-facing scene views. Mutable weather/time/mood/light state persists in `dnd5e_environment_state` at world, region, location, or scene scope; `EnvironmentStateService` merges those scopes as `scene > location > region > world > defaults`. Authored flavor entries live in content packages under `environment_flavors`, and explicit mechanical modifiers live under `environment_modifiers`.

`CharacterSceneViewService` now uses `EnvironmentDescriptionService` so `GET /api/play/current-scene` returns a richer `scene.description` plus an `environment` summary. Raw modifiers stay in inspectable `mechanical_details` when requested, not in the main narrative. See `docs/environment-context.md` and `docs/examples/environment-context/` for authoring examples and manual verification steps.

### NPC Schedules, Presence, And Routine Overrides

Stage 5J.3 adds authored NPC schedules and character-limited NPC presence. NPC templates can define default routines by 5J.2 time block, but mutable `dnd5e_world_entity_state` and explicit overrides beat the schedule. `CharacterSceneViewService` now returns `visible_npcs`, `known_relevant_npcs`, and NPC-derived affordances for visible interactable people.

NPC identity is character-perspective driven: unknown NPCs can appear as role or generic labels until the active character gains the authored knowledge that reveals a true name. Meaningful NPC state changes should go through `applyNpcStateMutation`, which creates `npc_state_changed` world events. See `docs/npc-presence.md` and `docs/examples/npc-presence/` for examples.

### Web Character Creation MVP

Stage 6B.1 adds the primary web character creation flow at `/play/create-character`. Firebase-authenticated players can create Quick Start, Guided, or Detailed-shell characters without SMS or phone setup. The backend validates final payloads and persists real `dnd5e_character`, class, item, and spell rows.

First characters become the active character automatically. Later characters do not overwrite the active character unless the player explicitly chooses Set as Active Character. Detailed mode supports Standard Array now and clearly labels granular skill/equipment/spell choices as recommended defaults until 6B.1D. See `docs/web-character-creation.md`.

### Web Character Management And Practical Sheet

Stage 6B.2 adds `/play/characters` and `/play/characters/:characterId` for authenticated players. The list and practical sheet use real backend `dnd5e_character`/read-model data, not fake Flutter state, and expose overview, ability scores, combat basics, features, proficiencies, equipment, spells, current adventure, and a light character-limited knowledge preview.

Active character switching is explicit. If the current active character has a submitted unresolved action, the UI asks for confirmation; switching does not cancel actions, move characters, or duplicate campaign state. Full sheet management is deferred to 6B.2D, and full campaign history/clues/knowledge are deferred to 6B.6. See `docs/web-character-management.md`.

### Campaign Dashboard And Adventure Entry

Stage 6B.3 makes `/play` the main player dashboard. It reads real backend account, active character, campaign, action, environment, and NPC preview state through `GET /api/play/dashboard`.

If the active character has no campaign, Start Adventure opens a lightweight intro first. Campaign assignment happens only after Begin Adventure calls `POST /api/play/start-adventure`; repeated starts resume the existing starter campaign instead of duplicating it. `/play/campaign` shows a light real campaign overview, and `/play/campaign/scene` shows the rich read-only current scene view powered by `GET /api/play/current-scene`. Action composition remains deferred to 6B.5. See `docs/web-campaign-dashboard.md` and `docs/web-rich-scene-view.md`.

The browser SMS simulator is available locally at:


No-CLI launcher:

```text

```

Double-click `Open SMS Simulator.cmd` from the project folder. It starts Docker Desktop if needed, brings up the backend/frontend stack, waits for the simulator route, and opens the browser automatically.

Neon-backed launcher:

```text
Open SMS Simulator - Neon DB.cmd
```

Double-click `Open SMS Simulator - Neon DB.cmd` when you want simulator actions to write to the hosted Neon database configured in `.env.production`. This mode uses `docker-compose.sms-neon.yml` to run only the local backend/frontend containers and passes `.env.production` into the backend. It does **not** start the local Docker Postgres `db` service. Use this intentionally: onboarding, character creation, campaign assignment, and beat advancement will create real rows in Neon.

It is a developer transport over the shared SMS pipeline:

```text
Simulator UI -> /api/dev/sms-simulator/inbound -> SmsInboundService -> persisted phone/account lookup -> onboarding/character/campaign/runtime services -> SmsOutboundFormatter -> SmsMessageStore -> polling UI
```

Enablement:

```env
ENABLE_SMS_SIMULATOR=true
SMS_SIMULATOR_DEV_PASSWORD=local_dev_only_change_me_if_enabled_in_production
```

The simulator is enabled by default outside production. In production it is disabled unless explicitly enabled, and then requires `x-sms-simulator-token` matching `SMS_SIMULATOR_DEV_PASSWORD`. The Firebase public landing-page deploy excludes `frontend/dev/**`.

Use the simulator to create real persisted test phone sessions, send numeric replies or commands (`HELP`, `STATUS`, `LEVEL`), test action-window thresholds, party defaults, catch-up summaries, combat beats, and compact level-up prompts. The default browser setup starts as a new phone so onboarding, `dnd5e_character` creation, campaign assignment, and runtime state all write to the real database. The player-facing message thread only displays rendered SMS text; internal state and database persistence checks live behind Show Debug and **Verify Persistence**.

Database target:

- `Open SMS Simulator.cmd` uses the local `.env`, currently intended for Docker Postgres at `db:5432`.
- `Open SMS Simulator - Neon DB.cmd` uses `.env.production`, intended for Neon via `DATABASE_URL=...neon.tech...`.
- Docker is not required by Neon itself; it is only the local app runtime for the simulator backend/frontend.

Stage 6A.4.5 makes ordinary valid SMS actions silent by default. A first valid action is persisted and visible in debug state, but the simulator does not send an immediate “Action recorded” SMS. Use the primary **Advance to Next Beat** button to deterministically close the current beat, apply missing defaults, resolve through `SmsSimulatorBeatCycleService`, and show the real authored result/next prompt without waiting for real time. Fake sessions without persisted numeric campaign and character context are rejected with debug reason `non_persistent_simulator_context`; they no longer produce generic success copy. Duplicate SMS action attempts in the same beat do not overwrite the original action: the first duplicate sends a web-app handoff link, and later duplicates are silently ignored. Repeated beat-advance clicks are idempotency-safe and report `already_resolved` instead of replaying result messages.

For Stage 6A.2 onboarding tests, keep `Real new-phone onboarding test (recommended)` checked before creating a session. The first inbound message creates/loads the persisted account state and sends `onboarding.welcome`; gameplay remains blocked until the user replies `START`.

Stage 6A.3 SMS character creation starts after onboarding intro with `character.mode_select`. Quick Start asks for name, species, and class, then applies smart defaults. Guided creation adds species lineage, attribute profile, background, and trait. Drafts persist as `dnd5e_character.status = draft` until confirmation, then become active SMS characters assigned to `account.active_character_id`.

Stage 6A.4 campaign assignment begins immediately after SMS character creation. The default configurable starter sends SMS-created characters into Greyvale / Shadows on the Grey Road at the Broken Caravan scene, creates a per-character campaign instance, initializes membership/objective/known context, sends `intro.world_entry` plus `intro.first_prompt`, then activates normal SMS pacing after the first intro fast-path action is recorded. Existing active campaigns resume instead of duplicating.

`STATUS` and similar non-substantive SMS requests are now daily-limited per user: first request returns a concise status plus `https://dailyttrpg.com/play`, second returns the link only, and third+ silently suppress outbound SMS while remaining visible in simulator debug. `HELP`, `STOP`, and gameplay replies are never blocked by this budget.

Stage 6A.5b makes normal exploration narrative-first. After the intro/tutorial beat, exploration prompts can omit repeated numbered menus and accept natural actions such as `inspect the wagon`, `follow the tracks`, or `talk to the innkeeper`. The deterministic resolver maps those inputs to active scene affordances and existing runtime interactions; it does not invent outcomes. Once-only affordances are hidden after successful use, ambiguous input asks a compact clarification question, and future AI resolver evaluation data is logged locally without external AI calls.

## Stage 1.5 Account And Character Lifecycle

DailyRPG now uses a phone-first account model that is ready for future SMS delivery work.

Account fields added for Stage 1.5:

- `phone_number` is required for new account creation
- `phone_number_normalized` stores a canonical lookup value such as `+15551234567`
- `phone_number_verified_at`
- `sms_opt_in_at`
- `sms_opt_out_at`
- `preferred_channel` defaults to `sms`
- `active_character_id` points to the current active character for the account

Character lifecycle behavior:

- Accounts can have multiple `dnd5e_character` rows
- Only one character per account can be active at a time
- The first character created for an account becomes active automatically
- Later characters are created inactive by default when an active character already exists
- Switching active characters is explicit through the API
- Characters are not hard-deleted in normal flow; they are marked inactive
- Inactivating the active character clears `account.active_character_id`

## Stage 2D D&D 5e Explicit Override Layer

Stage 2D adds an explicit, auditable exception system on top of the canonical 5e backend rules.

What the override layer is:

- the canonical rules engine still runs first
- overrides do not silently rewrite the base rules
- instead, explicit override records allow carefully scoped exceptions or effective-state adjustments
- every override keeps actor, reason, timestamps, target scope, and active state

Schema additions for Stage 2D:

- `db/init/006-stage-2d-overrides.sql`
- new table:
  - `dnd5e_override`

What override categories are supported now:

- `bypass_feat_prerequisite`
- `grant_illegal_spell`
- `bypass_spell_preparation_limit`
- `adjust_spell_slots`
- `override_inventory_item_uses`

- overrides are attached to a character

  - override metadata
- character detail reads now include an `overrides` array

## Stage 3A D&D 5e Derived Rules Engine

Stage 3A adds a centralized read-only rules engine layer that turns the Stage 2 data model into useful mechanical state without becoming the full gameplay engine yet.

What the derived rules engine is:

- a reusable backend engine layer for 5e mechanical derivation
- a clean way to ask what a character effectively has right now
- a light rules view that future command, gameplay, Twilio, and app clients can consume
- not the full combat engine, action system, or event loop

Schema changes for Stage 3A:

- none

Primary Stage 3A endpoint:

- `GET /api/dnd5e/characters/:id/rules`

Stage 2E integration:

- `GET /api/dnd5e/characters/:id/sheet` now also includes `data.derived_rules`

What the derived rules view computes now:

- total character level from `dnd5e_character_class`
- 5e proficiency bonus from total level
- ability modifiers from stored ability scores
- known feature-based ability score adjustments as separate source-aware data
- effective walk speed using stored character speed when present, otherwise race base speed plus seeded speed modifiers
- effective languages from manual and deterministic feature grants
- effective senses from seeded feature grants
- effective resistances from seeded feature grants
- feature-driven mechanical summaries for currently modeled effect types
- light mechanical completeness hints

Canonical/base vs effective/derived state:

- ability modifiers use the stored character ability scores as the canonical scores
- feature-based ability score bonuses are surfaced as known grants, but not automatically folded into stored scores because the current schema does not distinguish pre-grant vs already-applied scores
- movement exposes `race_base_speed`, `stored_character_speed`, `derived_from_race_and_features`, and `effective_speed`

## Stage 3B D&D 5e Atomic Command System

Stage 3B adds the first reusable gameplay command layer for DailyRPG.

What commands are:

- atomic low-level backend actions
- synchronous mutations against current character state
- reusable engine calls for later CLI, Twilio, and app clients
- not the future event/session system or high-level intent parser

Execution pipeline:

1. accept a structured command payload
2. load the current derived rules state for the character
3. validate the command against live state
4. apply the mutation through the existing Stage 2 and Stage 3 services
5. reload derived rules and return a structured result
6. record a light command log row for success or failure

Command request shape:

```json
{
  "type": "cast_spell",
  "characterId": 6,
  "actorAccountId": 9,
  "payload": {
    "spellId": 18,
    "slotLevel": 1,
    "slotPool": "standard"
  }
}
```

Schema changes for Stage 3B:

- `db/init/007-stage-3b-command-log.sql`
- new table:
  - `dnd5e_command_log`

Logging approach:

- command execution is logged to PostgreSQL in `dnd5e_command_log`
- each row stores `command_type`, `character_id`, `actor_account_id`, `payload_json`, `success`, compact `result_json`, `error_message`, and `created_at`
- logging is best-effort so a log write failure does not roll back a successful mutation

Stage 3B endpoints:

- `POST /api/dnd5e/commands/execute`
- `GET /api/dnd5e/characters/:id/command-logs`

Supported command types now:

- `cast_spell`
- `use_item`
- `move_item`
- `equip_item`
- `unequip_item`

Strict validation enforced now:

- unsupported command types are rejected
- `characterId` and payload ids must be positive integers
- commands only operate on existing characters and owned rows
- spell casts require an attached spell in a legal known/prepared state
- spell slot use respects current effective slot totals and remaining slots
- item use rejects impossible quantity and remaining-use states
- moving items rejects invalid parents and container cycles
- equipping a stored item is rejected
- existing override-aware behavior is reused where already modeled, including effective spell slots and overridden item uses

## Stage 3C Event / Session System

Stage 3C adds the first persistent gameplay event/session architecture for DailyRPG.

What the Stage 3C model is:

- `dnd5e_campaign` is the initial shared world scope
- `dnd5e_campaign_character` ties characters to a campaign
- `dnd5e_event_template` stores reusable event definitions
- `dnd5e_event_template_option` stores reusable option definitions for each template
- `dnd5e_event_instance` stores a concrete event created for one character inside one campaign
- `dnd5e_event_option` stores the copied persistent options for that concrete event
- `dnd5e_event_log` stores durable event history for creation, choice submission, and resolution

How campaign/session scope works in the initial version:

- the first implementation uses campaigns as the shared multiplayer-friendly world scope
- events are currently campaign-scoped and character-scoped at the same time
- a character can belong to a campaign and receive persistent events inside that campaign
- only one open event (`pending` or `active`) is allowed per character within a campaign at a time
- there is not yet a separate live session/presence table; that is deferred for later stages

How events are modeled:

- templates define the prompt and default options
- creating an event copies those options into the event instance so the exact historical options remain preserved
- choosing an option records the player-visible choice, resolves the effect, persists the result, and marks the event resolved
- event logs keep creation, choice submission, and resolution history in order

First supported event flow:

- template key: `roadside_cache`
- prompt: a hidden satchel is found beside the road
- options:
  - `take_coin_purse` grants `5 gp` and `2 sp`
  - `take_dagger` grants a `Dagger`
  - `leave_it` resolves with no state change

This is intentionally narrow but real:

- the event is persistent
- the options are persistent
- the outcome is persistent
- the currency/item effects are visible through existing inventory and sheet reads

## Stage 3D Gameplay Persistence & Progression System

Stage 3D makes gameplay consequences durable and queryable across commands, events, and progression writes.

What gameplay persistence means in the current backend:

- command execution already mutates canonical backend state synchronously
- event resolution already mutates canonical backend state synchronously
- Stage 3D adds a unified gameplay history feed so those mutations can be inspected in one place
- Stage 3D also turns `experience_points` into a first-class progression surface with service, API, and CLI support

What was added in Stage 3D:

- `dnd5e_gameplay_history` stores a unified character-scoped history stream
- command success/failure now records gameplay history in addition to `dnd5e_command_log`
- event creation and event resolution now record gameplay history in addition to `dnd5e_event_log`
- XP can be granted directly or through event resolution payloads
- XP changes are preserved on `dnd5e_character` and logged in gameplay history

How the gameplay history model works:

- each entry is tied to one character
- each entry stores:
  - `source_type`
  - `source_entity_id`
  - `action_key`
  - `summary`
  - `input_json`
  - `result_json`
  - `xp_delta`
  - actor account if available
  - timestamp
- supported `source_type` values in the current implementation:
  - `command`
  - `event`
  - `progression`
- history reads return newest-first so debugging and future replay tooling can inspect recent changes first

What progression support exists now:

- XP is stored in `dnd5e_character.experience_points`
- XP can be incremented through a dedicated service/API/CLI path
- event options can now grant XP
- XP changes are durable, queryable, and visible in gameplay history

## Stage 4A Narrative / Adventure Framework

Stage 4A adds the first location-based narrative layer on top of campaigns, events, commands, and progression. The backend now supports:

- persistent scenes tied to locations
- explicit scene transitions
- campaign-shared and character-specific story flags
- scene NPCs with stat-block-backed state
- quests and objectives
- skill-check-driven scene interactions
- narrative logs and movement history

The first seeded narrative slice is `Willowmere`:

- starting scene: `willowmere_square`
- progression scene: `waystone_road`
- alternate branch: `smugglers_cut`
- quest giver: `Elder Rowan`
- starter quest: `waystone_whispers`

### How scenes work

- A character belongs to a campaign through `dnd5e_campaign_character`.
- Stage 4A stores the character's current scene on that campaign membership row.
- Scenes are location-based, not a strict linear graph.
- Movement is only allowed through explicit `scene_transition` records.
- Each transition can carry:
  - required flags
  - required quest/objective states
  - required alignments
  - alignment recommendations

### How progression works

- Progression is guided, but not strictly linear.
- The backend evaluates scene, transition, and interaction availability from data stored in JSON conditions.
- Alignment influence is data-driven:
  - `required_alignment_abbreviations` can block or allow paths
  - `preferred_alignment_abbreviations` can mark a path as recommended
- Story flags and quest/objective states can unlock later scenes and interactions.

### How flags work

Flags are stored at two scopes:

- `campaign_flags`: shared world state for everyone in the campaign
- `character_flags`: state specific to one character inside that campaign

Examples in the Stage 4A seed data:

- `waystone_story_started`
- `rowan_trust`
- `waystone_glyphs_understood`
- `waystone_clue_found`

### How quests work

- `quest` rows define narrative arcs
- `quest_objective` rows define trackable steps
- `character_quest` and `character_objective` rows store per-character progress inside a campaign
- interaction outcomes can:
  - start a quest
  - complete an objective
  - complete a quest
  - update related flags and NPC state

### How interactions work

Stage 4A interactions are currently `skill_check` interactions.

An interaction attempts:

1. validate that the character is in the correct scene
2. validate availability conditions from flags, quests, objectives, and alignment
3. resolve a d20 roll
4. use Stage 3A derived stats to compute the modifier
5. persist the result
6. apply effects such as:
   - flags
   - NPC disposition changes
   - quest/objective updates
   - XP gains

The backend can accept a fixed `roll` for deterministic validation, or generate one automatically if no roll is supplied.

## Stage 4B Interaction System: Dialogue, Skill Checks, and Outcome Resolution

Stage 4B adds the first persistent dialogue layer on top of the Stage 4A narrative framework. The backend now supports:

- authored dialogue trees with nodes, options, and outcome definitions
- persistent dialogue sessions that survive across requests
- explicit and implicit skill checks
- visible and hidden checks
- short-term dialogue memory through session state
- long-term memory through campaign and character flags
- outcome-driven changes to flags, NPC state, quests, objectives, and XP
- player-triggered and system-triggered interactions

### Dialogue model

Stage 4B adds these backend tables:

- `dnd5e_dialogue`
- `dnd5e_dialogue_node`
- `dnd5e_dialogue_option`
- `dnd5e_dialogue_outcome`
- `dnd5e_dialogue_session`
- `dnd5e_dialogue_session_state`
- `dnd5e_dialogue_session_visit`
- `dnd5e_dialogue_session_choice`

How the model works:

- a `dialogue` defines a reusable conversation attached to a scene and optionally an NPC
- `dialogue_node` stores the text shown at each step
- `dialogue_option` stores what the player can choose next
- `dialogue_outcome` decides what happens after a choice, including node transitions and effects
- `dialogue_session` stores the active or completed playthrough of that authored dialogue for one character in one campaign
- session visits and choices are kept as durable history

### Skill check model

Dialogue skill checks use the Stage 3A derived rules engine.

Each dialogue option can define:

- `check_mode`
  - `none`
  - `explicit`
  - `implicit`
- `skill`
- `difficulty_class`
- `check_visibility`
  - `visible`
  - `hidden`

Stage 4B behavior:

- explicit checks pause the session and require a follow-up roll submission
- implicit checks resolve immediately when the option is chosen
- if no roll is supplied for an implicit check, the backend rolls automatically
- checks persist the roll, modifier, total, success/failure, and margin

### Memory model

Stage 4B uses two layers of memory:

- long-term memory
  - campaign flags
  - character flags
  - quest and objective state
  - NPC disposition/state
- short-term dialogue memory
  - `session_memory_json`
  - visited node keys
  - chosen option keys

This lets dialogue respond to:

- prior trust or hostility
- quest progress
- earlier lines in the same conversation
- whether a previous check succeeded or failed

### Outcome model

Dialogue outcomes are data-driven and can depend on:

- success/failure
- roll margin
- session memory
- visited nodes
- chosen options
- long-term narrative state

Outcomes can currently apply:

- `campaign_flags`
- `character_flags`
- `npc_states`
- `quests`
- `objectives`
- `xp`
- `session_flags`

### Trigger model

Stage 4B supports both:

- player-triggered dialogue
  - example: talking to `elder_rowan`
- system-triggered dialogue
  - example: entering `waystone_road` and auto-triggering `waystone_echo`

The first seeded Stage 4B slice includes:

- `elder_rowan_counsel`
  - a repeatable NPC dialogue in `willowmere_square`
  - supports branching trust, rebuff, and follow-up states

## Stage 4B.5 Combatant Stat Blocks & Action System

Stage 4B.5 adds the first shared combatant data layer for DailyRPG. The backend now supports a normalized, reusable, and automation-ready model for:

- stat blocks
- structured actions
- hybrid traits
- structured damage and effect payloads
- NPC and monster integration through a shared `dnd5e_stat_block` foundation

This stage does not implement combat yet. It prepares the data structures that Stage 4C can execute against.

### Core design

Stage 4B.5 uses a shared stat block foundation so NPCs and monsters can be read through the same automation-friendly shape.

Primary tables added:

- `dnd5e_stat_block`
- `dnd5e_stat_block_ability`
- `dnd5e_stat_block_skill`
- `dnd5e_stat_block_sense`
- `dnd5e_stat_block_resistance`
- `dnd5e_action`
- `dnd5e_action_damage`
- `dnd5e_action_requirement`
- `dnd5e_action_effect`
- `dnd5e_stat_block_action`
- `dnd5e_trait`
- `dnd5e_trait_effect`
- `dnd5e_stat_block_trait`
- `dnd5e_monster`
- supporting lookup tables:
  - `dnd5e_damage_type`
  - `dnd5e_sense_type`

Integration changes:

- `dnd5e_npc` now has `stat_block_id`
- `dnd5e_campaign_npc_state` now supports `current_hit_points`
- scene NPC reads now use the shared stat block model instead of the old NPC-only stat block table

### Stat block structure

`dnd5e_stat_block` stores the reusable combatant foundation:

- identity
  - `name`
  - `size`
  - `creature_type`
  - `alignment`
- defenses and vitality
  - `armor_class`
  - `hit_point_max`
  - `hit_dice_text`
- movement
  - `speed_walk`
  - `speed_fly`
  - `speed_swim`
  - `speed_climb`
- combat metadata
  - `proficiency_bonus`
  - `challenge_rating`
  - `xp_value`
  - `passive_perception`

Abilities and skills are normalized into child tables rather than embedded JSON.

### Action system

Actions are global definitions, then linked to stat blocks through `dnd5e_stat_block_action`.

`dnd5e_action` stores:

- action timing
  - `action_type`
- targeting/range
  - `range_type`
  - `range_normal`
  - `range_max`
- attack/save metadata
  - `requires_attack_roll`
  - `saving_throw_ability`
  - `saving_throw_dc`

Damage is normalized into `dnd5e_action_damage`.

Requirements and effects are stored separately:

- `dnd5e_action_requirement`
- `dnd5e_action_effect`

This keeps actions structured enough for future automation without hardcoding full combat execution yet.

### Trait system

Traits use the hybrid model:

- human-readable description in `dnd5e_trait`
- optional structured interpretation in `dnd5e_trait_effect`

Examples seeded in Stage 4B.5:

- `Nimble Escape`
- `Pack Tactics`
- `Keen Hearing and Smell`
- `Watchful Elder`

### Dice and damage model

Stage 4B.5 uses the hybrid dice approach:

- structured fields
  - `dice_count`
  - `dice_size`
  - `modifier`
  - `damage_type`
- human-readable text
  - `damage_text`

This keeps data usable both for automation and for later UI/text presentation.

## Stage 4C Combat Engine

Stage 4C adds the first real combat subsystem to DailyRPG. It is built as a specialized gameplay layer on top of the existing campaign, scene, event, command, stat block, and progression systems instead of as a disconnected mini-game.

What Stage 4C supports now:

- persistent combat instances
- persistent combat participants
- initiative and turn order
- explicit turn advancement
- basic structured attack actions
- hit or miss resolution
- damage application
- combat-local HP and defeat state
- simple rule-based AI turns
- combat resolution with persisted outcome data
- post-combat HP persistence and XP grants
- combat logging in campaign logs, gameplay history, and combat action logs

What is intentionally deferred:

- the full 5e combat ruleset
- reactions and opportunity attacks
- full condition handling
- resistances, immunities, and vulnerabilities during damage resolution
- movement, range enforcement, and positioning
- save-based action resolution
- spellcasting actions in combat
- rich tactical AI
- loot, escape, and full encounter authoring

### Combat model

Combat uses four new `dnd5e_` tables:

- `dnd5e_combat`
- `dnd5e_combat_participant`
- `dnd5e_combat_action_log`
- `dnd5e_combat_condition`

The combat record tracks the broader container:

- linked `campaign_id`
- linked `scene_id`
- optional linked `event_id`
- `status`
- `round_number`
- `current_turn_index`
- `current_participant_id`
- `visibility_mode`
- `auto_advance_turns`
- final `outcome_faction`
- final `result_json`

Participants track combat-local state:

- `entity_type`
- `entity_id`
- `stat_block_id`
- `initiative`
- `turn_order`
- `current_hp`
- `max_hp`
- `temporary_hp`
- `armor_class`
- `faction`
- `control_mode`
- `is_active`
- `is_defeated`

Combat is compatible with the narrative/event layer in a narrow first slice:

- combat can be linked to a campaign
- combat can be linked to a scene
- combat can be linked to an event through `event_id`
- only one open combat is allowed for a linked event at a time

Stage 4C does not yet auto-resolve event instances when combat ends, but it is ready for that follow-up.

### Implemented rules

Initiative and turn order:

- initiative is `1d20 + DEX modifier`
- turn order is persisted
- round and current turn index are persisted
- turns can advance explicitly with `end-turn`
- combat can auto-advance after actions if `auto_advance_turns` is enabled

Attack resolution:

- current participant must act on their turn
- defeated participants cannot act
- targets must be active participants in the same combat
- actions come from the Stage 4B.5 action system
- character participants use the seeded `Character Basic Strike`
- NPCs and monsters use their linked stat block actions
- attack rolls support deterministic overrides for testing
- damage rolls support deterministic overrides for testing

Hybrid visibility:

- each action stores `narrative_text`
- each action also stores `mechanical_detail_json`
- `visibility_mode = narrative` is the player-facing default
- `visibility_mode = debug` keeps the same narrative output but makes the full mechanics easy to inspect

Simple AI:

- AI acts only on AI-controlled participants
- it picks the first valid opposing target
- it picks the first attack-roll action available
- if no valid action exists, the AI fails cleanly instead of corrupting combat state

Combat completion:

- combat resolves when only one faction remains active
- character HP is written back to `dnd5e_character`
- campaign NPC HP is written back to `dnd5e_campaign_npc_state`
- defeated enemy XP is granted to winning character participants
- outcome is stored in `dnd5e_combat.result_json`

## Stage 4D Adventure State & Progression Engine

Stage 4D unifies the backend adventure systems into one centralized progression layer. Instead of dialogue, interactions, events, and combat each applying their own long-term consequences ad hoc, those systems now hand outcome payloads to a single progression service that updates:

- quest state
- objective state
- campaign truth flags
- character knowledge
- rewards
- scene unlock availability
- campaign log history

This keeps the backend as the only source of truth while making the world feel continuous instead of split into isolated subsystems.

### Progression model

Stage 4D uses the hybrid progression model required for DailyRPG:

- quests and objectives are the player-facing structure
- campaign and character flags are the system truth underneath
- objectives can update explicitly from authored outcomes
- objectives can also update implicitly when the engine re-evaluates conditions
- rewards and consequences are centralized and no longer applied independently by each subsystem

The central engine is in:

- `backend/src/services/adventureProgressionService.js`
- `backend/src/engine/adventure/progressionEngine.js`

### World truth vs character knowledge

Stage 4D now keeps a strict separation between:

- world truth
  - stored at the campaign level
  - uses `dnd5e_campaign_flag`
  - represents what is actually true in the shared campaign
- character knowledge
  - stored per character in `dnd5e_character_knowledge`
  - represents what this specific character knows, remembers, or has discovered

This is the foundation for:

- Twilio-friendly minimal summaries
- player-perspective reads that do not leak all GM state
- full admin/GM reads with complete campaign truth

## Stage 4E Playable Campaign Loop / Adventure Runtime Layer

Stage 4E turns the existing scene, dialogue, combat, event, and progression systems into a coherent playable loop. Instead of forcing a caller to manually inspect several subsystem endpoints, the new runtime layer answers:

- where the character is
- what mode they are currently in
- what thread is active right now
- what actions should be surfaced next
- what just changed

This is the backend layer that makes DailyRPG feel playable through API and CLI alone.

### Runtime model

Stage 4E introduces a centralized runtime service in:

- `backend/src/services/adventureRuntimeService.js`
- `backend/src/db/queries/adventureRuntime.js`

It assembles play state from:

- current scene and campaign membership
- active dialogue sessions
- active combat
- active events
- current objective/adventure state
- player knowledge vs full world truth
- recent meaningful history
- action-window and default-action policy state

The core play-state shape now includes:

- `current_scene_id`
- `current_mode`
- `active_dialogue_session_id`
- `active_combat_id`
- `active_event_id`
- `current_objective`
- `last_significant_update_at`
- `pending_action_window_id`

Modes currently surfaced:

- `exploration`
- `dialogue`
- `combat`
- `transition`
- `waiting`
- `event`

Modes matter, but they do not hard-lock behavior. The runtime foregrounds the actions that fit the current mode while still allowing valid out-of-mode actions when the underlying subsystem can accept them.

### Available action curation

Stage 4E does not dump every possible internal action. Instead, it curates a prioritized action list based on:

- current mode
- current scene
- active combat/dialogue/event state
- current objectives
- player knowledge
- urgency and thread continuity

Action categories currently surfaced include:

- scene movement
- talk to NPC
- scene interaction
- choose dialogue option
- attempt dialogue skill check
- start combat
- combat action
- end turn
- resolve AI turn
- wait

The list is intentionally mode-aware:

- combat actions are primary during combat
- dialogue options are primary during dialogue
- scene movement and local interactions remain visible as secondary actions when appropriate

This keeps the loop playable without boxing the player into a single rigid flow.

### Suggestions

Suggestions are sparse and secondary. The runtime may surface a soft nudge when it helps frame the next step, but it does not replace the actual action list.

Examples of current behavior:

- exploration contexts may suggest a likely lead
- dialogue, combat, and waiting states usually suppress suggestions so the action list stays clear

### Interruptions and carryover

Stage 4E now reasons about active threads instead of blindly resetting them.

Current behavior includes:

- starting combat during dialogue interrupts and cancels the active dialogue session
- moving to a new scene during dialogue interrupts and cancels the active dialogue session
- combat foregrounds the runtime while it is active
- waiting during an AI turn can resolve the AI action and hand control back to the player
- scene changes invalidate local opportunities that no longer make sense

Continuity is surfaced through a `continuity` section in play-state reads, with thread states such as:

- `resumable`
- `terminated`
- `transformed`

### Visibility layers

Stage 4E keeps the runtime explicitly layered:

- current context summary

- immediate action options
- recent result
- intended for future Twilio-style delivery

`player`

- character-perspective context

Player-facing views do not leak hidden world truth. Full mode is for debugging and future GM/admin surfaces.

## Stage 5A - World Model & Content Hierarchy

Stage 5A establishes the durable content/world foundation that later loading, authoring, and seed-campaign work can build on.

The locked hierarchy is now represented as:

```text
World
  Region
    Location
      Scene
```

The world is the top-level shared-state boundary. Campaigns now live inside a world, characters belong to one world, and characters participate in campaigns through memberships. Each character can be in multiple campaigns in that world, has exactly one active campaign context, and receives a default solo campaign as fallback free-roam context.

### Core model

Stage 5A added or aligned these concepts:

- `dnd5e_world` is the shared-world container.
- `dnd5e_campaign.world_id`, `slug`, `campaign_type`, and `status` make campaigns world-scoped and categorizable.
- `dnd5e_character.world_id` assigns each character to a world.
- `dnd5e_campaign_character` now stores campaign membership state, active context, default solo campaign marker, joined time, and left time.
- `dnd5e_region`, `dnd5e_location`, and `dnd5e_scene` form the world hierarchy.
- `dnd5e_region_template`, `dnd5e_location_template`, and `dnd5e_scene_template` preserve reusable template definitions.
- `dnd5e_world_entity` stores world-level NPC and monster instances with dynamic placement.
- `dnd5e_campaign_location_state` and `dnd5e_campaign_scene_state` store campaign overlays without mutating baseline world content.
- `dnd5e_world_flag` and `dnd5e_world_log` provide world-truth foundations distinct from campaign overlays and character knowledge.

Existing `dnd5e_npc` and `dnd5e_monster` rows act as reusable templates. `dnd5e_world_entity` is the mutable per-world instance layer, so changing or defeating an entity in one world does not alter the template or other future worlds.

### Template vs instance

Templates are reusable content definitions:

- NPC template: `dnd5e_npc`
- Monster template: `dnd5e_monster`
- Region template: `dnd5e_region_template`
- Location template: `dnd5e_location_template`
- Scene template: `dnd5e_scene_template`

Instances are runtime/world state:

- World entity instance: `dnd5e_world_entity`
- World region/location/scene baseline: `dnd5e_region`, `dnd5e_location`, `dnd5e_scene`
- Campaign overlays: `dnd5e_campaign_location_state`, `dnd5e_campaign_scene_state`

Runtime consequences should update instance or overlay state, not template definitions.

### World truth vs campaign overlays

Stage 5A separates state layers:

- World truth belongs to `dnd5e_world`, `dnd5e_world_flag`, `dnd5e_world_log`, and world entity placement/state.
- Campaign overlays belong to `dnd5e_campaign_location_state` and `dnd5e_campaign_scene_state`.
- Character knowledge remains in the existing character/campaign knowledge tables from Stage 4D.

This preserves the earlier visibility model: the world can have truth a character does not know yet, while campaigns can discover or alter locations/scenes independently.

### Campaign membership rules

The database now enforces:

- campaign and character memberships must belong to the same world
- a membership current scene must belong to the same world as the campaign
- only one active campaign context is allowed per character
- only one default solo campaign is allowed per character
- default solo membership must point to a campaign with `campaign_type = solo`

New characters automatically get a default solo campaign and membership.

## Stage 5B - Content Authoring Structure

Stage 5B defines the canonical authoring grammar for DailyRPG content packages. This is the human/AI author-facing layer: how to write worlds, scenes, transitions, quests, objectives, dialogue graphs, interactions, conditions, effects, and text layers as JSON before Stage 5C validates and imports them.

The full authoring reference lives at:

- `docs/content-authoring/README.md`
- `docs/content-authoring/templates/*.json`

### Authoring principles

- Content is JSON only for now.
- Packages are world-scoped under `content/worlds/<world_slug>`.
- Slugs are the stable content identity; content files never use database IDs.
- Templates remain reusable definitions; runtime/world/campaign state remains mutable instance data.
- Conditions are structured JSON, not prose.
- Effects are centralized declarations. Content says what should happen; engine/progression services execute it.
- Dialogue is graph-based.
- Scenes define explicit authored opportunities while the runtime may add implicit/system opportunities later.
- Text is layered so the same authored object can support SMS-style summaries, richer app prose, logs, and debug/GM notes.

### Canonical package folders

```text

  worlds/
    emberfall/
      manifest.json
      world.json
      templates/
        regions/
        locations/
        scenes/
      campaigns/
      regions/
      locations/
      scenes/
      transitions/
      entity_templates/
        npcs/
      world_entities/
      quests/
      interactions/
      dialogue/
      campaign_overlays/
        locations/
        scenes/
```

Folders are convention-discovered and optional unless the package needs that content type. `manifest.json` can override load order or include/exclude sections.

### Shared object conventions

Most authored objects use:

- `slug`: lowercase stable external key
- `name`, `title`, or `label`: human-facing display string
- `text`: layered prose
- `tags` or metadata fields only where supported
- `conditions`: structured availability/completion checks
- `effects`: structured consequences/rewards
- references by slug, such as `scene_slug`, `quest_key`, `objective_key`, or `npc_template_slug`

### Text layers

Supported `text` keys are:

- `title`: compact title
- `short`: SMS/UI-friendly line
- `summary`: short summary
- `full`: rich narrative
- `entry`: scene/node entry copy
- `sms`: extra compact future Twilio copy
- `recap`: log/history copy
- `success`: success result copy
- `failure`: failure result copy
- `gm_notes`: author/GM notes
- `variants`: conditional text variants for later runtime selection

Example:

```json
{
  "short": "Study the red motes in the weeds.",
  "summary": "Inspect the ember-sign near Ashford Crossroads.",
  "full": "Study the red motes drifting through the roadside weeds and look for a repeating mark.",
  "success": "You spot a faint rune pattern in the drifting cinders.",
  "failure": "The motes scatter before you can make sense of them."
}
```

### Reusable authoring patterns

Recommended current patterns:

- Talk-to-NPC unlocks clue: dialogue reveals knowledge and sets a character flag; transitions/interactions require that flag.

- Diplomacy branch: dialogue success sets trust flags; failure can change NPC state or prepare combat later.
- Delivery/rescue quest: quest starts through dialogue, objectives complete through scene entry or interactions, rewards apply through effects.
- Hidden path: transition requires a character flag or objective completion and provides only a sparse recommendation.

Deeper inheritance/composition is intentionally deferred. For now, reuse means copying clear patterns and keeping slugs predictable.

## Stage 5C - Content Tooling: Importer, Validation, and Package Loading

Stage 5C adds the first data-driven content pipeline. World content now lives on disk as JSON packages, is validated before any database write, and imports transactionally with slug-based upserts. This keeps authoring out of engine code while respecting the Stage 5A split between reusable templates and mutable world/campaign instances.

### Package structure

Packages are world-scoped and live under `content/worlds/<world_slug>`. The sample package is `content/worlds/emberfall`.

```text

  worlds/
    emberfall/
      manifest.json
      world.json
      templates/
        regions/
        locations/
        scenes/
      campaigns/
      regions/

      scenes/

      entity_templates/
        npcs/
      world_entities/
      quests/
      interactions/
      dialogue/
      hooks/
      campaign_overlays/
        locations/
        scenes/
```

Discovery is convention-based by default. `manifest.json` can provide package metadata, include/exclude sections, and override load order when a package needs more control.

### What imports now

The current importer supports these sections:

- `world` -> `dnd5e_world`
- `templates/regions` -> `dnd5e_region_template`
- `templates/locations` -> `dnd5e_location_template`
- `templates/scenes` -> `dnd5e_scene_template`
- `campaigns` -> `dnd5e_campaign`
- `regions` -> `dnd5e_region`
- `locations` -> `dnd5e_location`
- `scenes` -> `dnd5e_scene`
- `transitions` -> `dnd5e_scene_transition`
- `entity_templates/npcs` -> `dnd5e_npc`
- `world_entities` -> `dnd5e_world_entity`, optionally syncing scene NPC presence
- `quests` -> `dnd5e_quest` and `dnd5e_quest_objective`
- `interactions` -> `dnd5e_scene_interaction`

- `campaign_overlays/locations` -> `dnd5e_campaign_location_state`
- `campaign_overlays/scenes` -> `dnd5e_campaign_scene_state`

No Stage 5C schema migration was required. The importer writes into the Stage 5A and earlier gameplay tables.

### Validation rules

Validation runs before import and blocks all writes on failure. The validator checks:

- JSON parses cleanly and each file has the expected object or array shape
- required fields such as `slug`, `name`, and section-specific references exist
- slugs use stable external keys instead of numeric database IDs
- enum-like values are valid, such as campaign type, entity type, disposition, status, and interaction type
- duplicate slugs are rejected in the relevant package scope
- references resolve before import, including region/location/scene hierarchy, templates, world entities, quests, skills, interactions, and campaign overlays
- illegal template/instance mixups are rejected, such as a world entity pointing at a missing template

The broken validation fixture at `content/worlds/emberfall-broken-reference` intentionally references a missing region so contributors can see the failure shape.

### Import order

The default deterministic load order is:

1. `world`
2. `regionTemplates`
3. `locationTemplates`
4. `sceneTemplates`
5. `campaigns`
6. `regions`
7. `locations`
8. `scenes`
9. `sceneTransitions`
10. `npcTemplates`
11. `worldEntities`
12. `quests`
13. `interactions`
14. `dialogues`
15. `contentHooks`
16. `campaignLocationStates`
17. `campaignSceneStates`

The manifest can override or narrow this order, but dependencies still have to resolve before import.

### Upsert behavior

Content packages never refer to database IDs. They use slugs and keys, and the importer maps those to IDs internally during the transaction.

Re-import is safe and repeatable:

- if a slug/key exists, the row is updated
- if a slug/key does not exist, the row is created
- package import is all-or-nothing
- `--dry-run` performs discovery, validation, reference checks, and planned create/update reporting without writing

Because Stage 5A intentionally preserved legacy global key constraints for `dnd5e_location.key` and `dnd5e_scene.key`, imported location and scene keys still need to be globally unique for now. Future runtime work can relax that once all lookups are fully world-scoped.

### Template vs instance

The package structure keeps reusable definitions separate from mutable world state:

- `templates/*` loads reusable region/location/scene templates.
- `entity_templates/npcs` loads reusable NPC templates.
- `regions`, `locations`, and `scenes` load world baseline instances linked back to templates when supplied.
- `transitions` loads authored movement options between scene instances.
- `world_entities` creates mutable per-world NPC or monster instances with placement/state.
- `dialogue` loads graph-based dialogue definitions tied to scenes and NPC templates.
- `campaign_overlays/*` stores campaign-specific discovery and availability state without mutating world baselines.

Runtime consequences should continue to update world/campaign instance data, not package template definitions.

## Stage 5D - Dynamic Content Hooks

Stage 5D is the runtime activation layer for authored content. Content packages can now declare hooks in `content/worlds/<world_slug>/hooks`, import them into `dnd5e_content_hook`, and let the playable runtime evaluate them at meaningful lifecycle points. Hook effects are still applied through the centralized Stage 4D progression/effect engine; hooks never mutate state directly.

### Standard hook points

Supported hook points are:

- `scene_enter`
- `scene_exit`
- `dialogue_node_enter`
- `dialogue_option_select`
- `interaction_attempt`
- `interaction_success`
- `interaction_failure`
- `combat_start`
- `combat_end`
- `objective_start`
- `objective_complete`
- `time_beat`
- `event_triggered`
- `event_resolved`

Each hook has a `scope_type`, optional scope references such as `scene_slug` or `campaign_slug`, shared `conditions`, shared `effects`, optional `event_triggers`, feedback text, priority, and active state.

Example:

```json
{
  "slug": "ashford-crossroads-entry",
  "hook_point": "scene_enter",
  "scope_type": "scene",
  "scene_slug": "ashford-crossroads",
  "campaign_slug": "emberfall-solo",
  "label": "Ashford Crossroads entry memory",
  "conditions": {
    "forbidden_character_flags": {
      "ashford_crossroads_seen": true
    }
  },
  "effects": {
    "character_flags": {
      "ashford_crossroads_seen": true
    }
  },
  "feedback": {
    "sms": "The ember-sign stirs as you arrive.",
    "summary": "The ember-sign marks this place as important."
  },
  "priority": 20
}
```

### Condition evaluation

Stage 5D adds a centralized dynamic condition evaluator over the Stage 5B condition grammar. It evaluates conditions against the active runtime context:

- character alignment
- campaign type/status
- campaign flags as world/campaign truth
- character flags as player-known/discovered state
- quest and objective state
- current scene and current location state
- world entity state in the active context
- character knowledge entries

The runtime currently reevaluates broadly inside the active context: current campaign, current character, current scene, scene opportunities, entities, and imported hooks. This is intentionally simple and inspectable now, with room for dependency-targeted reevaluation later.

### Effect execution path

All content-driven effects follow this path:

```text
authored hook/effect
  -> dynamicContentService
  -> applyAdventureOutcome
  -> flags / quests / objectives / rewards / knowledge / campaign log
  -> active context reevaluation
```

This preserves the Stage 4D rule that rewards and consequences are centralized. Hook execution writes `content_hook_executed` campaign logs for debugging and future recap surfaces.

### Dynamic scene refresh

After a hook executes, the runtime refreshes the active scene summary. The refresh reports visible interactions, visible transitions, visible NPCs, and a hook execution summary. In the Emberfall sample, successfully inspecting the ember-sign sets `ember_sign_inspected`, which immediately reveals:

- the `read-ember-afterglow` follow-up interaction
- the `follow-old-kiln-road` transition
- a content-triggered `waystone_insight` event

### Events from content

Hooks may create first-class event instances through `event_triggers`. Events remain separate records and are not buried inline in hook effects.

Example trigger:

```json
{
  "event_template_key": "waystone_insight",
  "conditions": {
    "forbidden_character_flags": {
      "waystone_event_seen": true
    }
  },
  "feedback": {
    "sms": "A waystone choice opens.",
    "summary": "The ember-sign has opened a waystone event."
  }
}
```

If the character already has an open event, the trigger is skipped cleanly and reported instead of crashing the hook pass.

### Time beats

Stage 5D supports discrete `time_beat` hook execution through CLI/API. This is not a background scheduler yet. It establishes the backend model needed for future missed-response windows, default actions, and async world cadence.

The Emberfall sample includes `hooks/ember-sign-time-beat.json`, which sets the campaign-level world-truth flag `ember_sign_intensified` after the character has inspected the ember-sign.

### Feedback layers

Hook feedback supports concise and richer surfaces:

- `minimal`: SMS-style concise narration
- `player`: narrative-first player output without hidden debug internals
- `full`: debug/GM-style output with hook ids, hook points, scope, priority, and blocked reasons

No Twilio or Flutter integration is implemented in this stage.

## Stage 5E: Runtime Content Orchestration

Stage 5E adds the live orchestration layer that makes imported content, dynamic hooks, play state, dialogue, combat, events, objectives, and progression feel like one coherent adventure runtime.

This stage does not define new content formats and does not import content. Instead, it assembles the current playable moment from existing systems and shapes it into a single runtime output for future SMS, app, and debug/GM surfaces.

### Runtime service

The Stage 5E orchestration service lives in:

- `backend/src/services/runtimeContentService.js`

It consumes:

- Stage 4E play-state from `adventureRuntimeService`
- Stage 5D dynamic scene and hook reevaluation from `dynamicContentService`
- Stage 4D progression, objectives, knowledge, and recent-result state
- active dialogue, event, combat, and scene context already surfaced by Stage 4E

Routes and CLI commands remain thin. They call the orchestration service rather than rebuilding runtime logic.

### Core runtime output

The orchestrated runtime output includes:

- `identity`: campaign and character identity
- `runtime_state`: current mode, current scene, active dialogue/combat/event ids, action window id, and last significant update
- `scene`: assembled current scene context, visible entities, interactions, transitions, and narrative text
- `active_thread`: selected primary thread plus secondary/candidate threads
- `opportunities`: primary, secondary, system, and full/debug opportunity sets
- `objectives`: current objective, active quest slice, and recent meaningful progress
- `continuity`: sticky-context and interruption reasoning
- `default_action`: action-window default, suggested action, and system fallback
- `dynamic_content`: active hook reevaluation summary
- `presentation`: concise narrative, richer app-style view, and debug metadata where allowed

### Scene plus active thread model

Runtime is always grounded in the current scene. Active threads can temporarily take presentation priority.

Baseline priority is:

1. combat
2. event
3. dialogue
4. waiting or transition
5. exploration

Contextual scoring can adjust the selected focus. For example:

- active combat becomes urgent and foregrounded
- active dialogue remains sticky while the player is in the conversation
- an active event becomes primary when it is waiting for a choice
- exploration remains available as secondary context during dialogue

The selected thread is inspectable in `active_thread.primary`, and the scoring/debug view is available with `mode=full` or `show-runtime-debug`.

### Opportunity curation

Stage 5E gathers valid opportunities from:

- scene transitions
- scene interactions
- NPC dialogue entry points
- active dialogue options and checks
- active event options
- combat actions
- runtime/system actions such as `wait`
- Stage 5D dynamic scene refresh state

Each opportunity is classified with:

- `thread_type`
- `urgency`
- `relevance_score`
- `curation_reasons`

The runtime then surfaces a curated set:

- `primary`: foreground choices for the active thread or current scene
- `secondary`: valid contextual choices that still preserve player agency
- `system`: fallback/runtime actions
- `all`: full inspectable list, included in full/debug views

The runtime avoids dumping every possible internal option into the player-facing surface. It also avoids hard-locking the player into one path unless the underlying subsystem requires it.

### Dialogue integration

Dialogue is now treated as an active runtime thread, not as a disconnected mini-mode.

When a dialogue session is active:

- the current scene remains visible
- the dialogue node text becomes the main context summary
- available dialogue options become primary opportunities
- scene movement and interactions remain secondary where valid
- the action window tracks the dialogue choice/check
- default fallback currently resolves to `wait`, with future support for user-defined defaults

If combat or movement interrupts dialogue, the older Stage 4E interruption handling still cancels or transforms the dialogue thread and Stage 5E reports that continuity state.

### Objective surfacing

Objectives remain explicit but are surfaced selectively.

The runtime shows:

- current objective when one is active
- a short active quest slice
- recent progression results such as objective completion, event reward, or dialogue start
- a `surfacing_policy` that explains whether objective display is quiet or currently relevant

This keeps future SMS/app views from spamming quest state every turn while still showing meaningful updates.

### Combat integration

Combat remains owned by the Stage 4C combat engine. Stage 5E only orchestrates presentation:

- active combat becomes the primary thread
- player combat actions become primary opportunities on the player turn
- AI/other turns surface continuation or waiting actions
- scene and dialogue context remain available only as secondary context where valid
- after combat resolves, the runtime reassembles the scene and progression state from existing persisted results

Stage 5E does not add new combat rules.

### Context continuity

Continuity uses a sticky-by-default model.

The runtime keeps the current thread in focus unless:

- a higher-priority thread appears
- the player explicitly shifts focus
- the thread resolves
- movement invalidates the thread
- combat or an urgent event interrupts the thread

The output includes `continuity.model`, `continuity.persisted_threads`, `continuity.selection_reason`, and `continuity.contextual_overrides` so debugging does not require guessing why focus changed.

### Default actions and async foundation

Stage 5E builds on the Stage 4E action-window tables. No new schema was required.

The default-action model is layered:

1. future user-defined preference
2. current action-window default
3. context-aware suggested action
4. system fallback, usually `wait`

The runtime returns:

- the open action window
- the suggested action
- the selected default action
- the reason the fallback was chosen

This is the foundation for future missed-response windows and asynchronous party play. There is still no background scheduler in this stage.

### Presentation layers

Stage 5E produces one core runtime object and shapes it into layered views:

- `minimal`: concise narrative, current context, primary choices, and default action
- `player`: richer scene/thread/opportunity/objective view without hidden internals
- `full`: debug/GM-style view with scoring, blocked dynamic hooks, full play-state, and dynamic reevaluation detail

This keeps the backend from creating competing runtime truth models for SMS, app, and debug clients.

## Stage 5F: World Simulation And Cross-Player Impact

Stage 5F turns Emberfall into a bounded shared world instead of a set of isolated campaign reads.

What Stage 5F adds:

- classified world-change propagation with `campaign_local`, `regional`, and `global` scopes
- event-sourced shared-world truth through `dnd5e_world_change`
- persistent world-entity evolution through `dnd5e_world_entity_event`
- knowledge propagation that remains separate from world truth
- progression windows that gather responses before defaulting unresolved participants
- catch-up summaries that explain both world changes and any default action taken on a character's behalf

### Core model

Shared world truth now lives in:

- `dnd5e_world_change`
- `dnd5e_world_flag`
- `dnd5e_world_entity`
- `dnd5e_world_entity_event`
- `dnd5e_world_propagation_receipt`

Async response orchestration now lives in:

- `dnd5e_progression_window`
- `dnd5e_progression_window_participant`
- `dnd5e_progression_window_response`
- `dnd5e_default_action_application`
- `dnd5e_character_catchup_ack`

World truth and player knowledge remain separate:

- world truth is stored as event-sourced world changes plus the current projected flag/entity state
- player knowledge is stored as `dnd5e_character_knowledge`
- propagation receipts describe what could become known, when, and by which channel

### Propagation classification

Stage 5F uses an explicit propagation scope on every world change:

- `campaign_local`: the change only propagates to that campaign's active members
- `regional`: the change targets active memberships currently in the affected regional context
- `global`: the change targets active memberships across the whole world

Important guardrail:

- `campaign_local` changes may not directly mutate shared world truth through `world_flags` or `entity_updates`
- this prevents accidental leakage of local-only state into the shared world projection

### Knowledge propagation

Knowledge propagation is hybrid and inspectable:

- direct observation: same-scene observers discover the change immediately
- delayed awareness: `time_delay` receipts can become available later
- rumor/system channels remain available for future content-specific behavior
- propagation is explicit and can be advanced through CLI or API

The system now records:

- what changed
- who directly knew
- who only had an available receipt
- when delayed knowledge became discoverable

### World event progression

Stage 5F currently models world-event progression through event-sourced `dnd5e_world_change` records plus discrete `trigger-world-beat` steps.

That means:

- world events are inspectable as change history
- time beats are first-class progression records
- world flags and entity changes can advance on those beats

A separate `dnd5e_world_event` lifecycle table is intentionally deferred for a later Stage 5 pass.

### Persistent world entities

World entities are now operational shared actors:

- they live at the world level, not inside scenes
- they can move and change state through world changes
- scenes surface or hide them based on current world placement

In the Emberfall validation flow, moving `mara-voss-at-crossroads` from scene `4` to scene `9` immediately removed Mara from Ashford Crossroads in other campaigns because scene reads now respect `dnd5e_world_entity.current_scene_id`.

### Async progression fairness

Progression windows are designed to avoid both common async failures:

- the world does not wait forever for an inactive player
- the game does not default a player too early

The Stage 5F rule is:

- responses may accumulate while the threshold has not been reached
- unresolved participants are not defaulted before the threshold
- once the threshold is reached, unresolved participants receive a traceable default action
- catch-up reads show exactly what happened later

## Stage 5H: Character Advancement And Level-Up System

Stage 5H adds a full advancement pipeline instead of a simple XP counter. It supports milestone progression, event-weighted XP, and future GM-controlled grants while keeping level-up player-triggered, resumable, and safe around async gameplay.

What Stage 5H adds:

- campaign and world advancement mode configuration
- centralized XP and milestone grant auditing
- D&D-style threshold evaluation with pending level-up availability instead of auto-leveling
- persistent, resumable level-up sessions
- fixed-or-rolled HP choice with server-side audit logging
- validated spell selection with SMS-curated subsets and full app/debug spell lists
- soft party sync and catch-up multipliers for lagging characters
- runtime surfacing for `level_up_available`, pending levels, safe-moment gating, and deferred reasons

### Advancement modes

Supported advancement modes:

- `event_weighted_xp`: default mode for normal play; XP can come from objective, quest, combat, discovery, dialogue, system, or future GM sources
- `milestone`: creates pending level-up availability directly without requiring an XP threshold
- `gm_controlled`: represented in config now so future GM tooling can grant XP or levels without redesigning the backend

Configuration lives at world and campaign scope through:

- `dnd5e_world.advancement_mode`
- `dnd5e_world.advancement_config_json`
- `dnd5e_campaign.advancement_mode`
- `dnd5e_campaign.advancement_config_json`

Current default config shape:

```json
{
  "advancement_mode": "event_weighted_xp",
  "xp_weights": {
    "objective": 100,
    "quest": 300,
    "combat": 50,
    "discovery": 75,
    "dialogue": 25,
    "system": 25,
    "gm": 100
  },
  "catch_up_enabled": true,
  "soft_sync_enabled": true,
  "catch_up_multiplier_per_level_gap": 0.25,
  "catch_up_multiplier_cap": 1.75
}
```

### XP grants and thresholds

XP is granted through the centralized advancement service and recorded in `dnd5e_advancement_event`. Each grant stores:

- `character_id`
- `world_id`
- `campaign_id`
- `source_type`
- `source_entity_id`
- `amount_xp`
- `reason`
- `dedupe_key`
- advancement metadata such as catch-up multiplier or HP roll context

Duplicate grants are prevented through `dedupe_key` when the source is meant to pay only once, such as an objective completion.

The threshold table currently supports levels `1-20`:

```text
1: 0
2: 300
3: 900
4: 2700
5: 6500
6: 14000
7: 23000
8: 34000
9: 48000
10: 64000
11: 85000
12: 100000
13: 120000
14: 140000
15: 165000
16: 195000
17: 225000
18: 265000
19: 305000
20: 355000
```

Crossing a threshold does not level the character automatically. Instead, the system sets:

- `dnd5e_character.level_up_available = true`
- `dnd5e_character.pending_level_count > 0`

Large XP or milestone grants can create more than one pending level, and the player can resolve those levels one safe step at a time.

### Level-up flow and safe moments

Level-up is always player-triggered. The runtime will surface availability, but it does not interrupt combat, dialogue, scene flow, or async progression windows.

Safe-moment behavior:

- safe now: idle, post-combat, post-thread resolution, or explicit quiet moments
- deferred: active combat, active dialogue, active event, active action window, or active progression window
- the runtime explains why leveling is deferred instead of forcing the change mid-thread

Persistent level-up sessions live in `dnd5e_level_up_session` and move through these practical states:

- `started`
- `awaiting_choice`
- `validating`
- `ready_to_finalize`
- `completed`
- `deferred`
- `canceled`

Each session stores:

- `from_level`
- `target_level`
- `current_step`
- required steps
- selected choices
- validation state
- HP method and roll result
- chosen subclass or spells where relevant
- final preview and completion timestamps

### HP choice: fixed or roll

The player chooses one HP method per level-up:

- `fixed`: uses class hit die average plus Constitution modifier where supported
- `roll`: rolls server-side using the class hit die and logs the result in `dnd5e_advancement_event`

Important rules:

- roll happens on the server
- roll result is stored and auditable
- reroll is blocked
- max HP updates only when the level-up finalizes atomically

Validated examples from the local stack:

- Fighter level 1 -> 2 with fixed HP resolved to `+7`
- Sorcerer level 1 -> 2 with a server-side `d6` roll of `3` resolved to `+4` including Constitution

### Spell selection and interface shaping

The backend computes the full valid spell list from class, spell level, current spells, and level-up requirements. Then presentation is layered:

- SMS-style flow: small curated subset of valid choices only
- app/debug flow: full valid list with spell metadata

Rules enforced:

- no invalid spell ids or slugs
- no off-list spells
- no wrong-level spells
- no duplicate picks unless a rules path explicitly allows them later
- non-casters do not receive spell-pick steps

The current Stage 5H validation path covers:

- Fighter flow with no spell choice required
- Sorcerer flow with full valid spell list, curated SMS subset, invalid selection rejection, and final spell persistence

### Feature handling

Stage 5H uses the existing class, subclass, and override infrastructure instead of mutating derived stats directly.

What is implemented now:

- automatic level gains are computed from existing class/subclass data
- subclass choice is supported when required by the current class level
- duplicate feature grants are prevented during finalization
- finalized level-up writes update the composition state and derived character read models

Important limitation:

- the framework is in place, but exhaustive hand-authored class feature coverage is still deferred to later content/rules work; Stage 5H validates representative fighter and sorcerer paths instead of pretending every class feature tree is already complete

### Soft party sync and catch-up

Party members do not hard-lock to the same level. Instead:

- the campaign computes highest, lowest, average, and median level
- lagging characters can receive a catch-up multiplier on eligible XP grants when enabled
- higher-level characters are never penalized
- the multiplier is capped to avoid runaway catch-up loops

The Stage 5H default catch-up behavior is:

- `+0.25` multiplier per level of lag
- capped at `1.75x`

Example validated locally:

- a quest grant with base XP `300` became `375` for a lagging sorcerer because the catch-up multiplier resolved to `1.25x`

### Runtime integration

Stage 5H now appears in both the Stage 4E play-state layer and the Stage 5E runtime orchestration layer.

Runtime outputs now include:

- `level_up_available`
- `pending_level_count`
- `can_start_level_up_now`
- `level_up_deferred_reason`
- `active_level_up_session_id`

The richer Stage 5E runtime also includes an `advancement` block so future SMS/app surfaces can decide whether to show:

- a quiet note that a level-up is available
- a deferred message explaining why it must wait
- an active level-up session that can be resumed later

## Stage 5I: Encounter Scaling And Balance

Stage 5I adds a bounded encounter scaling layer between authored content, runtime orchestration, combat, async pacing, and Stage 5H advancement. It does not generate encounters freely and it does not override story intent. Authors define the encounter, its allowed scaling methods, solo safeguards, pacing target, valid resolution paths, and one equivalent reward value.

What Stage 5I adds:

- `dnd5e_encounter_template` for imported encounter templates by world and slug
- encounter content section: `encounters/`
- strict encounter template validation in the Stage 5C package validator
- simple v1 party strength evaluation from party size and character levels
- transparent encounter power and difficulty scoring
- scaling priority: authored variant selection, enemy count adjustment, then bounded stat tweaks only when allowed
- explicit solo-safety warnings and fail-forward checks
- async beat target validation
- equivalent reward resolution for combat and non-combat paths through Stage 5H XP grants
- CLI/API preview and resolution tools

### Encounter Template Format

Encounter JSON lives under package paths such as:

```text
content/campaigns/shadows_grey_road/encounters/grey-road-encounters.json
```

Minimal structure:

```json
{
  "encounter_id": "shrine-rusk-confrontation",
  "name": "Rusk at the Shrine",
  "campaign_slug": "shadows_grey_road",
  "scene_slug": "shrine-ruins",
  "encounter_type": "story",
  "difficulty_intent": "hard",
  "scaling_enabled": true,
  "story_fixed_by_default": true,
  "explicit_story_scaling": true,
  "allowed_scaling_methods": ["variant_selection", "enemy_count"],
  "party_size_range": { "min": 1, "max": 4 },
  "level_range": { "min": 1, "max": 3 },
  "async_beat_target": { "min": 4, "max": 6 },
  "base_variant": "solo",
  "variants": [
    {
      "variant_id": "solo",
      "party_size_range": { "min": 1, "max": 1 },
      "enemies": [
        { "entity_slug": "rusk-bandit", "entity_type": "npc_template", "count": 1, "base_power": 1.4 }
      ]
    }
  ],
  "resolution_paths": ["combat", "intimidation", "negotiation", "escape", "fail_forward"],
  "reward_value": {
    "xp": 150,
    "grant_on_resolution": true,
    "equivalent_across_paths": true
  },
  "fail_forward": true
}
```

Story-critical encounters are fixed by default. Runtime scaling is allowed only when `scaling_enabled` and `explicit_story_scaling` are both true and only through `allowed_scaling_methods`.

### Scoring And Scaling

Party strength v1 uses only:

- party size
- average level
- highest level
- lowest level
- level spread
- effective party level
- `party_power = party_size * effective_party_level`

Encounter power v1 sums enemy `base_power * count`. If `base_power` is absent, the service derives a rough score from stat-block XP, challenge rating, hit points, and AC. The preview output always shows the calculation.

Difficulty labels are transparent:

- `trivial`
- `easy`
- `medium`
- `hard`
- `deadly`
- `story`
- `avoidable`
- `tutorial`

Scaling priority is always:

1. authored variant selection
2. bounded enemy count adjustment
3. bounded stat tweak, only if explicitly allowed

### Solo And Async Safety

Solo preview applies explicit warnings when:

- a solo character faces multiple enemies
- no escape, negotiation, stealth, avoidance, or fail-forward path exists
- a hard/deadly solo story encounter lacks fallback context

Async beat estimates are guardrails, not perfect simulation. Minor encounters should target 2-4 beats, and major/story encounters should target 4-6 beats. Debug preview warns if power or action economy is likely to exceed the authored target.

### Equivalent Rewards

Encounter rewards are outcome-based, not method-based. A resolved encounter may grant the same XP for combat, negotiation, intimidation, stealth, avoidance, investigation, or fail-forward resolution when the author sets `equivalent_across_paths`.

Rewards route through Stage 5H:

- source type: `encounter`
- source metadata includes `encounter_id` and `resolution_path`
- dedupe key prevents double-paying the same encounter for the same character/campaign
